# RE_020 · Excess draw calls with render thread saturated (not GPU-bound)

| Category | Severity | Fires while | Target |
|---|---|---|---|
| Rendering | High | Playing | 60 FPS only |

## What it means

Unlike RE_001, the bottleneck here is not the GPU — it's the cost of submitting so many draw calls from the render thread itself. That points to CPU-side overhead in the rendering pipeline, not to shading cost.

## When it fires

All of these are true at the same time, averaged over one second:

| Measurement | Looks for | What it is |
|---|---|---|
| Draw calls | High | Commands sent to the GPU this frame |
| Render thread time | High | Time the render thread spends building the frame for the GPU |
| GPU bound | No | The GPU is not what limits the frame |

This rule only applies to a 60 FPS target. The plugin hides it entirely when the project's target frame rate is set to 30 FPS, where the same measurement can still fit the budget.

## Why it happens

Each draw call carries a fixed CPU cost to build and submit, independent of the GPU's own cost to execute it. With draw calls this high, that submission overhead alone can saturate the render thread even while the GPU still has room.

## How to fix it

1. **Reduce draw call count via instancing**, the same fix as RE_001, but here it relieves the render thread instead of the GPU.
2. **Check whether the RHI Thread is enabled and balancing the load correctly.**
3. **Profile the command submission phase with Unreal Insights.**

## How to confirm the fix

Watch **Draw Calls** and **Render Thread** in Live Metrics. Once draw calls fall back under the rule's threshold or the render thread returns under its budget, the rule stops firing and its row in Diagnostics is no longer marked active.
