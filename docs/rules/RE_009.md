# RE_009 · Game thread saturated — CPU-bound (60 FPS)

| Category | Severity | Fires while | Target |
|---|---|---|---|
| CPU | Medium | Playing | 60 FPS only |

## What it means

The game thread alone is over the rule's limit for a 60 FPS target, and the GPU is not the reason. The cost is on the CPU side of gameplay: logic, physics, or Blueprints running on the main thread.

## When it fires

All of these are true at the same time:

| Measurement | Looks for | What it is |
|---|---|---|
| Game thread time | High | Time the main game thread spends this frame |
| GPU bound | No | The GPU is not what limits the frame |

This rule only applies to a 60 FPS target. The plugin hides it entirely when the project's target frame rate is set to 30 FPS, where the same measurement can still fit the budget.

## Why it happens

Ruling out the GPU points squarely at CPU-side gameplay code: Tick functions doing more than they need to every frame, expensive physics queries, or Blueprint graphs evaluated on every tick instead of on an event.

## How to fix it

1. **Profile with the `stat game` console command or Unreal Insights** to isolate the most expensive function on the game thread.
2. **Review Tick() on actors and components** — move logic that doesn't need to run every frame to a Timer with a lower frequency.
3. **Check the Gameplay Profiler panel for Blueprints with heavy per-frame logic** — it breaks tick cost down by class.

## How to confirm the fix

Watch **Game Thread** in Live Metrics. Once it falls back under the rule's limit, the rule stops firing and its row in Diagnostics is no longer marked active.
