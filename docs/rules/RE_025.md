# RE_025 · High texture memory correlated with a slow GPU

| Category | Severity | Fires while | Target |
|---|---|---|---|
| Memory | High | Playing | 30 FPS and 60 FPS |

## What it means

Unlike RE_007 and RE_008, which only look at how much VRAM textures are using, this rule crosses that with a GPU time that's actually slow — pointing at texture streaming or bandwidth as a probable cause of the measured GPU cost, not just a capacity risk.

## When it fires

All of these are true at the same time:

| Measurement | Looks for | What it is |
|---|---|---|
| Texture memory | High | VRAM currently committed to texture data |
| GPU bound | Yes | The GPU, not the game thread, is what limits the frame |
| GPU time | High | Time the GPU spends on this frame |

## Why it happens

When texture memory is high and the GPU is measurably slow at the same time, the streaming pool is a likely culprit: if it keeps swapping mips in and out because it's undersized for what's on screen, that thrashing shows up as GPU time, not just as memory used.

## How to fix it

1. **Check the Texture Streaming Pool for thrashing** — mips loading and unloading repeatedly.
2. **Prioritize Virtual Texturing on the largest textures**, if the project supports it.
3. **Profile with Unreal Insights whether GPU time concentrates on texture sampling.**

## How to confirm the fix

Watch **GPU Time** and the texture rows in the Memory section of Live Metrics. Once GPU time falls back under the rule's threshold, the rule stops firing and its row in Diagnostics is no longer marked active.
