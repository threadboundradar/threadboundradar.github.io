# RE_031 · High texture memory without measured GPU impact

| Category | Severity | Fires while | Target |
|---|---|---|---|
| Memory | Low | Playing | 30 FPS and 60 FPS |

## What it means

A contrast with RE_025: a lot of texture memory is reserved, but GPU time is low. This usually means memory over-provisioning — textures bigger than necessary — rather than an active performance problem.

## When it fires

All of these are true at the same time:

| Measurement | Looks for | What it is |
|---|---|---|
| Texture memory | High | VRAM currently committed to texture data |
| GPU time | Low | Time the GPU spends on this frame |

## Why it happens

Reserving VRAM for a texture doesn't by itself cost GPU time — it costs GPU time only when it's sampled, evicted, or streamed under pressure. A low GPU time alongside high reserved memory means the textures are sitting there without causing measurable slowdown yet.

## How to fix it

1. **Audit whether the high VRAM use actually translates into visual benefit**, or is waste.
2. **Treat this as low immediate risk** — prioritize it after the rules that flag active performance problems.

## How to confirm the fix

Watch the texture rows in the Memory section of Live Metrics. Once texture memory falls back under the rule's threshold, the rule stops firing and its row in Diagnostics is no longer marked active.
