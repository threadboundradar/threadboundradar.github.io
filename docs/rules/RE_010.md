# RE_010 · Critical game thread saturation — CPU-bound (30 FPS)

| Category | Severity | Fires while | Target |
|---|---|---|---|
| CPU | High | Playing | 30 FPS and 60 FPS |

## What it means

The game thread alone is taking longer than even a 30 FPS frame allows, and the GPU is not the reason. This is RE_009's pattern at a severity that compromises the lowest reasonable target.

## When it fires

All of these are true at the same time, averaged over one second:

| Measurement | Looks for | What it is |
|---|---|---|
| Game thread time | High | Time the main game thread spends this frame |
| GPU bound | No | The GPU is not what limits the frame |

## Why it happens

Ruling out the GPU points squarely at CPU-side gameplay code: Tick functions doing more than they need to every frame, expensive physics queries, or Blueprint graphs evaluated on every tick instead of on an event — at a cost severe enough on its own to miss a 30 FPS budget.

## How to fix it

1. **Profile with the `stat game` console command or Unreal Insights** to isolate the most expensive function on the game thread.
2. **Review Tick() on actors and components** — move logic that doesn't need to run every frame to a Timer with a lower frequency.
3. **Check the Gameplay Profiler panel for Blueprints with heavy per-frame logic** — it breaks tick cost down by class.

## How to confirm the fix

Watch **Game Thread** in Live Metrics. Once it falls back under the 30 FPS frame budget, the rule stops firing and its row in Diagnostics is no longer marked active.
