# RE_024 · Early signal of fill-rate / post-process bound

| Category | Severity | Fires while | Target |
|---|---|---|---|
| Rendering | Low | Playing | 60 FPS only |

## What it means

The early version of RE_015: GPU time is already notable despite low draw calls and triangle count, though the frame still meets budget. Worth reviewing post-process cost before it becomes a problem.

## When it fires

All of these are true at the same time:

| Measurement | Looks for | What it is |
|---|---|---|
| GPU time | High | Time the GPU spends on this frame |
| Draw calls | Low | Commands sent to the GPU this frame |
| Triangles drawn | Low | Triangles submitted this frame, counted once per rendering pass |
| Frame time | Low | Total time to produce this frame |
| GPU bound | Yes | The GPU, not the game thread, is what limits the frame |

This rule only applies to a 60 FPS target. The plugin hides it entirely when the project's target frame rate is set to 30 FPS, where the same measurement can still fit the budget.

## Why it happens

Fill-rate cost scales with pixels shaded, not with geometry — so a scene with little geometry can still carry a meaningful GPU cost from post-processing or render resolution alone, before it ever becomes a budget problem.

## How to fix it

1. **Review the chain of active Post Process Volumes as a preventive practice.**
2. **Monitor this metric as more full-screen effects get added** to the scene.

## How to confirm the fix

Watch **GPU Time** relative to **Frame Time** in Live Metrics. Once GPU time falls back under the rule's threshold, the rule stops firing and its row in Diagnostics is no longer marked active.
